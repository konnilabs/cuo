# CUO security model

CUO 0.2.0 is a public-source development preview for a local single-host MVP, not a stable security-supported release. Do not expose the internal Core or Agent ports. The repository maintainer is [konnilabs](https://github.com/konnilabs). A confidential reporting channel is not configured yet: GitHub private vulnerability reporting was disabled when checked on 2026-11-01. Enabling it and documenting a tested reporting route is a stable-release prerequisite. Do not post credentials or nonpublic exploit details in public issues.

## Trust boundaries

* The browser is untrusted. HttpOnly / SameSite Strict cookies identify sessions; Secure is mandatory for HTTPS ingress. Loopback HTTP is the deliberate local-install exception. Sessions expire after twelve hours and can be revoked. The BFF checks exact Origin and a per-session CSRF token before authenticated mutations. Passwords use scrypt with per-user random salts; tokens are not put in localStorage.
* The BFF owns users and sessions in a separate SQLite database. It supplies Core principals from the session; browser-provided role headers are never forwarded. All Core mutations require idempotency keys. Unknown operations are rejected by an explicit route allowlist.
* The Core is an independent headless Go engine. A separate random bearer token authenticates internal BFF requests. Viewer, Operator, Administrator and Owner permissions and local-host authorization are checked again in the Core. Durable audit events do not contain raw Docker configurations or registry tokens.
* The Agent alone mounts the Docker socket. A different random bearer token authenticates its four typed routes: health, info/inventory, registry scan and update execution. There is no generic Docker proxy, arbitrary shell endpoint or host-file editor. A managed-container label, policy, digest, platform and drift checks are required before disruption.

Docker socket possession is effectively host authority. The agent is **not** an OS security sandbox. Trusted project source files may contain secret interpolation and powerful Docker settings; only host-owner-approved Compose sources belong in the registered projects directory. Keep its read-only mount narrow. Untrusted users must never be allowed to upload Compose projects into that directory.

## Rendering and component contracts

The RMT document owns the shell, routing state, selectors, intents and widget lifecycle. The static Maraca registry is built from `console/components/manifest.json`. Custom widgets use `xtend.component.contract.v2` and `xtend.rmt.component-contract.v1`, with a typed `vm` contract projected through a JSON `data-view` attribute. JSON parsing never evaluates code. The emitted `xtend-command` event contains `{kind,value,id,data}`; RMT maps it to a registered AppService. Components never write into surrounding shell DOM.

Each widget owns only its shadow-root physical nodes and native draft/focus behavior. Its small keyed reconciler creates native elements and text nodes; it preserves nodes, input drafts and native dialog modal state. Event listeners are disposed using an AbortController. Optional `footer` slot content is host-authored. Table output is bounded to eight rows per page, dashboard log output to twelve visible entries, and the full Logs terminal to the bounded 200-event view buffer.

Native dialog `showModal/close`, the Toast host’s manual `showPopover/hidePopover` top-layer presentation, and calendar arrow-key focus are the reviewed imperative integrations. They affect only physical focus / modal presentation inside the component and do not own application navigation or visibility. Visibility remains in RMT. Untrusted image references, logs, actor names and registry errors become text nodes, never markup.

The deployed CSP disallows remote scripts, inline scripts, object embedding and framing. It requires Trusted Types where supported. Inline **styles** remain allowed because XTend XIcon creates a local style element and sets documented icon variables. No remote fonts or script CDNs are used.

The pinned framework contains legacy raw-HTML paths that CUO does not use. `console/tools/harden-runtime.mjs` replaces the two actual assignment sites in the emitted runtime with fail-closed errors, records before/after hashes, and rejects any unreviewed HTML sink. This is an explicit deployment adaptation; the pinned external source dependency is unchanged. Switching the application to legacy HTML templates requires a separate security review and is unsupported. The framework's legacy `x-input` HTML implementation is not included in CUO's selected component graph.

## OIDC and profiles

OIDC configuration is Owner-only and CSRF protected. Provider configuration is a trust decision: configured HTTPS discovery/token/JWKS URLs may reach internal self-hosted identity services. Use a trusted provider and valid server certificates. Browser tokens, Core tokens and provider client secrets never enter the RMT view model. Secrets are stored in the restricted identity database and therefore included in protected backups. Login transactions are one-use, browser-bound and expire after five minutes. Signed ID tokens must match issuer, audience, expiry and nonce. Identities use the issuer/subject pair; email is never used for implicit linking. Provisioning defaults to Viewer on the local host; enabling broader default roles is an explicit Owner decision. Provider session logout and back-channel revocation are not implemented; CUO sessions retain their documented lifetime/revocation rules.

`CUO_OIDC_ALLOW_HTTP=1` exists solely for isolated local provider tests and is not enabled by Compose or installation. Production provider endpoints always require HTTPS. Local development preferences may use localStorage in the demo; no credentials are stored there. Profile edits cannot alter login names, roles or host access. Notification dismissal changes only per-user display records, not Core jobs or audit events.

The real XRouter/XDrawer receive a hash-checked static-DOM adaptation at build time, with text-only router errors and no Trusted Types bypass or permissive HTML policy. See `console/reports/xtend-dom-adaptations.json`.

## Execution and recovery

Updates use immutable per-platform registry manifests. Public registry authentication realms are constrained to the registry host, with Docker Hub's documented `auth.docker.io` exception; redirects and unknown registries are rejected. Private registry credentials are not yet supported. Image healthcheck output and Docker error response bodies are not returned to users.

The agent rechecks the running image and configuration after pulling. It preserves actual volume names and runtime overrides. It retains the old standalone container stopped, with restart policy disabled. Database/volume rollback is deliberately not automatic. Interrupted executions require intervention and are protected against duplicate agent replay by durable journals. BFF disconnect does not cancel an already durable job.

The first explicit execution permission is `permissions.readOnlyHostMonitoring`, disabled by default. Only an Owner may grant or revoke it on a policy for a specific existing, accessible container, with a reason and warning acknowledgement. Global, host and group grants are invalid; the resolver independently strips broad grants. Permission changes are audited. Administrators may preserve a grant while editing ordinary policy fields but cannot change or retarget it. The Core sends the current resolved permission when execution starts, so queued jobs do not retain a revoked grant. Already-started operations continue under their admission decision. The public job API cannot supply Agent permissions.

With this grant, existing bind mounts of host `/proc` and `/sys` subtrees may be retained when Docker inspection explicitly reports `RW: false`. This is an update of the approved workload's existing access: source, destination and read-only status are preserved and checked for drift. A missing or malformed `RW` field does not grant this exception. Writable host-system mounts, host root/devices/Docker data, Docker sockets, and mount destinations within the container's own `/proc`, `/sys` or `/dev` trees remain blocked. Paths are normalized before classification. This rule applies to any managed monitoring workload and contains no image- or vendor-specific exception. Each additional operation or permission class requires its own implementation and validation; the permission model is not a generic shell or Docker API endpoint.

Agent journals and Compose desired-state files are persisted; the latter may contain resolved environment secrets. Protect `/data`, backups and `.env` accordingly. There is no automatic retention pruning yet. Backup scripts stop only CUO, never managed workloads. Restore requires explicit terminal confirmation because it replaces application data.

Offline backup tools resolve the selected Compose instance's actual named volumes and use its immutable installed Core image ID without pulling. Backup validation stages the entire archive in a private temporary directory, rejects traversal, links, duplicate entries and unsupported file types, verifies gzip completeness, SQLite integrity/supported schemas and Agent JSON, and refuses unfinished Core jobs. Restore validates again before copying, sets ownership for the supported image users and retains a mode-0600 pre-restore snapshot. Three-volume replacement is not atomic: on a copy error CUO remains stopped for manual recovery. Backups are plaintext secrets; filesystem mode 0600 does not provide encryption. The restore test uses disposable volumes and no host Docker socket; it does not certify application-data rollback or recovery from host failure.

## Dependency and release review

The Compose backport resolves CVE-2026-78669 and passes the local image HIGH/CRITICAL threshold. The final Go binary scan, with upstream's compiler/linker configuration and retained symbols, reports zero affected symbols. GO-2026-5932 (unmaintained OpenPGP), GO-2026-6860 and GO-2026-6866 (HTML processing) remain module-version findings; Trivy assigns UNKNOWN severity. They are recorded without suppression in `reports/compose-govulncheck.txt`; the tool reports that this executable does not appear to call the affected code. This assessment is scoped to the recorded binary and must be repeated for the final release digest and future dependency/build changes.

The Agent's Compose plugin is rebuilt from upstream v5.6.1's immutable source commit with a narrowly scoped dependency backport of upstream security commit `7ad5c58b380038aed842bc1396b091e81a88a0b0`. It identifies itself as `v5.6.1-cuo.1`; it is not an official Docker release. `dependencies/compose/compose.lock` pins source/patch, exact toolchain version and resulting module-file hashes. Only go.mod/go.sum change; the three module updates are x/net v0.60.0, x/crypto v0.57.0 and x/text v0.42.0, with upstream companion checksums. The plugin uses pinned Go 1.26.10 matching upstream, retained symbol information, module verification and readonly resolution. CUO's own binaries remain on Go 1.27.3. The runtime ships source references, licenses of linked modules, actual build info and a binary hash. `tools/verify-compose.mjs` checks the executable itself and runs Go binary SCA before CI's real Compose reconciliation test. CUO owns maintenance of this backport until a tested patched official release replaces it; details are in [dependencies/compose/README.md](dependencies/compose/README.md).

`third_party/` contains the Watchtower source snapshot and retained licenses. XTend is an external source dependency pinned by repository, immutable commit and archive SHA-256 in `console/xtend.lock.json`. The resolver verifies downloads before extraction, never deletes the target of a pre-existing symlink, and preserves replaced dependency directories in an ignored cache. No mutable branch or unverified archive is accepted. The selected XTend workspaces use their upstream npm lockfile and installation scripts are disabled. Only the modified Watchtower configuration-override algorithm is compiled into CUO; the upstream Watchtower daemon, webhook handlers, notification stack and their dependency graph are not linked. The source commit is `a047c7f9ff11813f930f6998863fa1b8a015985c`.

The original XTend workspace includes MCP-server packages unrelated to this product. The build selects only Maraca/CLI/RMT/compiler workspaces. The deployed Node process uses Node built-ins, bundled Maraca server-service host files and the pinned OIDC runtime tree (`openid-client`, `oauth4webapi`, `jose`) from `console/runtime/package-lock.json`. This runtime tree is separately audited. Record build-tool audit results separately from runtime applicability, never silently suppress findings.

CI checks source and output sinks, Go tests/race checks/vet, typed services, RMT lint, build contracts, dependencies, secret patterns and isolated backup/restore. A separate manual read-only preflight scans image OS/runtime packages and emits CycloneDX inventories from the same Docker image archives. Scanner failures or any HIGH/CRITICAL finding fail that gate, including unfixed findings. Exceptions require a separate documented, evidence-based review; no ignore list is supplied. The Console runtime omits package managers and uses a digest-pinned Alpine Node image; the Agent patches OS packages and omits unused Buildx. Package installation still resolves upstream repositories at build time, so local builds are not claimed to be bit-for-bit reproducible.

The old publication draft scanned a local build and then rebuilt for push; its scan therefore did not cover the published artifact. `tools/release.sh` now exits without publication. Stable OCI distribution still requires build-once digest-preserving promotion, verified signatures, complete reviewed SBOM coverage, provenance and the remaining gates in [RELEASE-GATES.md](docs/RELEASE-GATES.md). A passing source CI run or locally generated inventory is not release approval.
